# HU-10 - Preparar una nueva evaluación crediticia

## Recorrido y alcance

Analista activo -> Nueva evaluación -> readiness HU-08 -> documento -> expediente existente o datos mínimos -> finalidad/monto -> revisión/consentimiento -> caso preparado.
El inicio de HU-09 y su layout se reutilizan. El administrador institucional no recibe permisos de analista.
El caso se guarda como DRAFT. HU-10 no llama Bank Mock, no crea FinancialProfile, no genera recomendaciones y no consume cuotas por procesamiento.

## Persistencia y seguridad

Clients es dueño del expediente; Evaluations coordina el caso y consume ApplicantRecords por su contrato público.
La búsqueda siempre incluye tenantId autorizado por InstitutionSessionGuard y TenantContextGuard. Tanto lectura por ID como creación requieren ANALYST activo.
La fuente de readiness es TenantPreparationService de HU-08, comprobada antes del formulario/búsqueda y al confirmar.
En el submit final se bloquea el tenant para coordinarse con cambios de preparación. Client, Evaluation y AuditLog se escriben en DatabaseUnitOfWork; abandonar el formulario no crea expedientes.
La constraint (tenantId, documentType, documentNumber), upsert y serialización por tenant evitan duplicados. Si otro analista registró datos distintos, se solicita buscar y confirmar el expediente actual.
Un UUID por intención, bloqueo transaccional y Evaluation.idempotencyKey único recuperan el mismo resultado. requestFingerprint rechaza la reutilización de una clave con otro contenido, actor o tenant.
El snapshot congela identificación, nombres, nacimiento y teléfono leídos en el momento del submit. No depende de futuras modificaciones del Client.
Consentimiento aprobado: “Confirmo que el solicitante autorizó la consulta de su información financiera para esta evaluación.”
Evidencia existente: consentGivenAt del servidor y createdByMembershipId (actor y tenant). No se añaden versiones legales, IP, KYC ni evidencia regulatoria.
Los campos nuevos de Client son opcionales en la base para preservar expedientes anteriores; los solicitantes nuevos requieren nombres, apellidos y nacimiento.

## Datos y validación

Solo PERSON. Documentos soportados: CI, PASSPORT, OTHER; NIT no se ofrece como documento de persona.
Se valida formato básico y longitud del modelo, no un algoritmo de identidad boliviano. CI admite números y complemento alfanumérico con guion.
Nombres/apellidos admiten Unicode, espacios, apóstrofes y guiones. Fecha real no futura; teléfono opcional sin letras.
Finalidades: WORKING_CAPITAL, GREEN_PROJECT, BUSINESS_INVESTMENT, EQUIPMENT, OTHER, del enum vigente. Compra de vehículo no existe en ese enum.
Dinero como texto decimal -> Prisma Decimal(14,2); positivo, hasta dos decimales. El límite de dígitos es capacidad del almacenamiento, no una regla crediticia.
El wizard usa estado React en memoria, conserva respuestas al volver y regresa directamente al resumen después de Modificar. Cambiar documento limpia los datos personales anteriores y revoca la confirmación de consentimiento.
Las llamadas institucionales tienen timeout de 15 segundos. El caso preparado se recupera en /{slug}/evaluaciones/{id}, incluso después de recargar.

## API / Swagger

- GET /api/institution/tenants/{tenantSlug}/evaluations/preparation
- POST /api/institution/tenants/{tenantSlug}/evaluations/lookup
- POST /api/institution/tenants/{tenantSlug}/evaluations
- GET /api/institution/tenants/{tenantSlug}/evaluations/{id}

DTOs documentados en Swagger; campos desconocidos rechazados por validación existente. Mutaciones protegidas por origen y X-DoggyCredit-Institution. Sin tenantId editable.
400: entrada inválida o consentimiento faltante; 403: falta de rol/membresía; 404: caso/expediente ajeno o ausente; 409: readiness o conflicto de intención/expediente.
Migración: 20261006000000_evaluation_preparation (Client.firstName, lastName, birthDate; Evaluation.requestFingerprint). No elimina ni reescribe datos históricos.
