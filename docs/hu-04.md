# HU-04: Completar la contratacion del plan

Implementacion en `feature/hu-04-contracting`. Referencias: Sprint 1 corregido y los cuatro mockups de confirmacion de plan, metodo, pendiente y confirmado. No incluye aprovisionamiento HU-05 ni pagos reales. Arquitectura: [ADR-003](architecture/ADR-003-contracting-mock-payments.md).

## Recorrido

1. Iniciar sesion como OPERATOR y abrir una solicitud APPROVED. Generar y abrir/copiar su enlace de contratacion. No se envia otro correo.
2. El enlace se canjea una sola vez por sesion HttpOnly. Confirmar explicitamente un plan comercial; el interes registrado no lo contrata automaticamente.
3. Basico demo (0 BOB) confirma sin Payment. Profesional demo (349 BOB) y Empresarial demo (799 BOB) requieren pago mensual simulado.
4. Elegir transferencia, QR o tarjeta simulada. El servidor crea un intento PENDING usando el importe del snapshot, no datos comerciales del navegador.
5. Para transferencia, el operador simula el resultado en Administracion > Contrataciones, previa confirmacion. Para QR/tarjeta, abrir DoggyPay Demo y confirmar, rechazar o cancelar. No ingresar datos financieros reales.
6. La pantalla de contratacion consulta cada tres segundos mientras PENDING. PAID confirma la contratacion; FAILED/CANCELLED permiten otro intento sin perder historial. Detiene polling al terminar, desmontar o perder autorizacion.

## Configuracion

En `.env` de la raiz, sin versionar secretos:

```dotenv
PAYMENT_PROVIDER=mock
CONTRACTING_ACCESS_TOKEN_TTL_MINUTES=60
CONTRACTING_SESSION_TTL_MINUTES=60
MOCK_PAYMENT_CHECKOUT_TTL_MINUTES=15
SEED_DEMO_PLANS=true
PUBLIC_APP_URL=http://localhost:5173
```

Ejecutar `npm run prisma:deploy`, `npm run prisma:generate` y `npm run prisma:seed`. El seed de planes solo se permite en development/test, es idempotente y no modifica planes existentes. Los planes demo son ejemplos del kata, no un catalogo comercial definitivo. Las migraciones conservan solicitudes y datos previos; no hacer reset.

Para un telefono en la misma Wi-Fi, configurar ademas `MOCK_PAYMENT_PUBLIC_URL=http://<IP-LAN-del-PC>:5173` en la raiz. En `apps/web/.env`:

```dotenv
VITE_API_URL=/api
DEV_HOST=0.0.0.0
```

Reiniciar los procesos de desarrollo si estaban levantados. Vite reenvia `/api` al backend local, evitando que el telefono intente llamar a su propio localhost. El QR contiene la URL de DoggyPay con un token de corta duracion; no contiene una orden bancaria. El representante puede seguir usando localhost en el PC. Si Windows bloquea el acceso, habilitar solo el puerto de desarrollo en el perfil privado y verificar que el router no aisle clientes; no desactivar el firewall. No usar Wi-Fi publico. Una IP cambiante requiere actualizar la variable y regenerar el QR.

El origen configurado es una URL base sin ruta, credenciales, query ni fragmento. En produccion debe ser HTTPS; PAYMENT_PROVIDER es disabled por defecto. No hay tunel ni despliegue publico incluido. La app de produccion necesita reverse proxy para `/api` cuando usa URL relativa; el proxy de Vite solo corresponde al desarrollo.

## API

Todas las rutas tienen prefijo `/api`. Los POST administrativos/representante exigen Origin permitido y `X-DoggyCredit-Admin: 1`; datos adicionales se rechazan.

| Metodo y ruta                                             | Autorizacion / entrada                               | Resultado                                                      |
| --------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------- |
| POST `/admin/institution-requests/:id/contracting-access` | Operador, cuerpo vacio                               | Enlace de un solo uso; revoca anteriores                       |
| POST `/contracting/access`                                | `{token}`, rate limit                                | Cookie de sesion; no devuelve token de sesion en JSON          |
| GET `/contracting/context`                                | Cookie de contratacion                               | Institucion propia, planes disponibles, snapshot y ultimo pago |
| POST `/contracting/plan`                                  | Cookie, `{planId}` UUID                              | Confirmacion idempotente del mismo plan                        |
| POST `/contracting/payment`                               | Cookie, `{method}`, header `Idempotency-Key` UUID v4 | Mismo intento si se repite; un solo pendiente                  |
| POST `/contracting/payment/checkout`                      | Cookie, cuerpo vacio, rate limit                     | Rota enlace/QR del pago pendiente                              |
| GET `/contracting/payment/status`                         | Cookie                                               | Estado minimo de contratacion y pago                           |
| GET `/admin/contractings?page=1`                          | Operador                                             | Paginacion de 10, historial de intentos                        |
| POST `/admin/contractings/payments/:id/simulate`          | Operador, `{result}`                                 | Resultado de transferencia simulado                            |
| GET `/mock-payment-provider/checkout`                     | Header `X-DoggyPay-Token`                            | Importe, referencia, metodo, estado, vencimiento; sin PII      |
| POST `/mock-payment-provider/checkout/result`             | Mismo header, `{result}`                             | Resultado durable del mock, procesado por negocio              |

Metodos: BANK_TRANSFER, QR, CARD. Resultados de simulacion: PAID, FAILED, CANCELLED. Errores: 400 validacion, 401 sesion/acceso, 403 autorizacion/CSRF, 404 recurso o mock deshabilitado, 409 estado incompatible, 410 checkout vencido, 429 limite de solicitudes, 503 inicializacion recuperable. Un fallo de proveedor conserva el intento PENDING y permite reintentar inicializacion; no implica cobro ni confirmacion.

## Persistencia y recuperacion

Migracion `20260927004235_hu04_contracting_payments` agrega los campos comerciales de Plan, Contracting, Payment, ContractingCredential, PaymentProviderEvent y MockPaymentCheckout. Decimal(14,2) se mantiene; importes por API son strings. Un indice parcial impide dos pagos pendientes de la misma contratacion. Snapshot y referencias historicas no se reescriben al modificar un plan.

No guardar enlaces de acceso/checkout en logs, capturas de diagnostico compartidas, almacenamiento web ni Git. El frontend retira el fragmento inmediatamente. Recargar DoggyPay requiere escanear nuevamente; recargar contratacion conserva la sesion y permite regenerar el enlace. No se puede reconstruir un token a partir de su hash.

El usuario confirmo tambien el pago simulado desde su telefono fisico en la misma Wi-Fi, usando el caso ficticio "Demo HU04 Wi-Fi". Ese registro se conserva para inspeccion manual; no corresponde a una solicitud real.

Limitaciones deliberadas: sin pasarela real, webhooks externos, conciliacion automatica, pagos recurrentes, provisioning, activacion de suscripcion ni invitaciones institucionales. Los reintentos procesan resultados durables del mock; no hay cola/worker nuevo. Admin/publico son contextos de acceso, no tenants ficticios.
