# HU-06: Activar cuenta del administrador institucional

Fuente funcional: Sprint 1 corregido, Documento Maestro y [ADR-004](architecture/ADR-004-durable-provisioning.md). Identity & Tenants consume la `MembershipInvitation` emitida en HU-05; Audit escribe el hecho de activación. No se crea otro tenant, token ni sistema de sesiones.

## Flujo

El correo de HU-05 apunta a `/activar-cuenta#token=...`. React lee el fragmento (y admite `?token=` de enlaces anteriores), lo elimina inmediatamente de la URL y conserva el token solo en memoria. No usa Web Storage. `POST /api/membership-invitations/preview` valida sin consumirlo y devuelve únicamente nombre de institución, nombre/correo invitados, expiración y si requiere contraseña. `POST /api/membership-invitations/activate` revalida todas las condiciones.

La invitación liga exactamente User, Tenant y TenantMembership. Solo puede activarse una membership `INSTITUTION_ADMIN` inicial e `INVITED` para un tenant `ACTIVE`. Un User `BLOCKED` no se reactiva. Si User carece de contraseña, define una global y pasa a `ACTIVE`; si ya tiene credenciales, las conserva y solo activa la nueva membership. El `User.status` global no concede acceso al tenant. Se marca `MembershipInvitation.acceptedAt` una sola vez, se activa la membership y Audit escribe `MEMBERSHIP_ACTIVATED` con actor invitado, tenant, membership e invitación en una misma transacción. Un segundo envío recibe un error de enlace utilizado y no modifica nada.

El hash Argon2id existente usa 19456 KiB, timeCost 2 y parallelism 1. Se calcula **fuera** de la transacción, después de comprobar token y política. El backend exige 15-128 puntos de código Unicode después de NFC, sin recortar espacios ni exigir clases de caracteres. Una blocklist local pequeña compara la contraseña completa (insensible a mayúsculas) y no llama servicios externos; no pretende cubrir todas las credenciales comprometidas. La misma normalización NFC debe aplicarse al verificar contraseñas institucionales en HU-07.

La transacción final usa `updateMany` condicional para consumir la invitación y activar solo la membership asociada; revalida el usuario y no sobrescribe una contraseña establecida concurrentemente. Una auditoría fallida revierte todo. No hay login automático ni ruta institucional protegida: eso pertenece a HU-07.

## Seguridad y límites

Ambos endpoints son POST, sin cookies de activación; por ello no dependen de CSRF basado en cookie. Respuestas con `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, Helmet y CORS limitado al origen configurado. El limitador local por IP admite 60 solicitudes por 15 minutos y es best-effort por proceso, no una defensa distribuida. Producción exige HTTPS en `PUBLIC_APP_URL`; el despliegue debe terminar TLS también para la API. No se devuelven contraseñas, hashes, IDs internos ni roles globales. No se solicita institución, NIT, plan ni cargo al usuario.

Mockup 08 se implementa con datos reales. Mockup 11 no cambia: su indicador se basa en `TenantMembership.status` y pasa de «Invitación pendiente» a «Cuenta activa» tras HU-06. No hay migración nueva; `acceptedAt` y las relaciones existentes son suficientes. La contraseña nunca se guarda en claro. El enlace previo a HU-06 enviado por HU-05 sigue siendo válido dentro de su TTL de 48 horas por defecto.

## Verificación

`npm run test:e2e`, `npm test`, `npm run lint`, `npm run format:check` y `npm run build`. Las e2e usan PostgreSQL aislado y EmailSender simulado; cubren preview, estados inválidos, política/Unicode, User nuevo/existente, concurrencia, rollback de auditoría y el cambio de estado visible para OPERATOR. El frontend cubre eliminación del token de URL, contexto real, show/hide, usuario existente, errores y submit único.
