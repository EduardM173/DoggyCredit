# HU-05: Aprovisionar automaticamente una institucion habilitada

Implementada sobre SOA logico modular. Decisiones y propietarios: [ADR-004](architecture/ADR-004-durable-provisioning.md).

## Flujo y garantias

1. Solicitud APPROVED + Contracting CONFIRMED. Un plan de pago exige Payment PAID del mismo contrato, monto y moneda del snapshot; un plan gratuito no fabrica pagos.
2. Confirmar el contrato en HU-04 registra el job durable en su misma transaccion. Aprobar HU-03 por si solo no aprovisiona.
3. Worker reclama un job y verifica la elegibilidad por `ProvisioningPlans`; `planInterest` nunca define suscripcion, precio ni capacidades.
4. Transaccion unica: Tenant ACTIVE, User global nuevo INVITED (o reutilizado sin modificar datos/credenciales/rol/status), TenantMembership INSTITUTION_ADMIN INVITED marcada inicial, TenantSubscription ACTIVE del confirmedPlanId, MembershipInvitation vigente, auditoria SYSTEM y job COMPLETED.
5. Despues del commit, entrega recuperable de invitacion usando Resend. Membership sigue INVITED incluso si User ya estaba ACTIVE en otra institucion.

Un tenant por solicitud, job por contrato, membership por tenant/usuario, admin inicial por tenant, suscripcion inicial por contrato y suscripcion ACTIVE por tenant. Se comprueba compatibilidad antes de reutilizar datos existentes; los conflictos no se sobreescriben. Slug estable normalizado con sufijo de solicitud en colisiones; no es una credencial de acceso.

El plan confirmado y su snapshot son la referencia comercial. Cambiar precio/actividad del catalogo despues de contratar no cambia el derecho contratado. No se implementan capacidades comerciales todavia no definidas.

## Persistencia y recuperacion

Migracion `20260927020000_hu05_durable_provisioning`: job/enum, metadatos de entrega, marca de admin inicial, procedencia de suscripcion, constraints e indices parciales. Agrega pendientes para contratos historicos CONFIRMED, sin inventar fecha de aprobacion ni marcar pagos. No necesita reset ni db push. Datos historicos incompatibles con los nuevos indices requieren conciliacion explicita; no se eliminan automaticamente.

Estados: PENDING -> PROCESSING -> COMPLETED; errores transitorios -> FAILED_RETRYABLE con nextAttemptAt; errores permanentes o limite -> FAILED_PERMANENT. Lease vencido permite recuperar trabajo abandonado, con fencing por UUID. Los intentos no se reinician al reiniciar la API. Un rollback no deja entidades parciales ni auditorias huerfanas.

El registro MembershipInvitation funciona como entrega durable separada: sentAt confirma aceptacion por proveedor, no recepcion humana. lastSendErrorCode y nextSendAttemptAt permiten diagnosticar sin tokens. Fallos de correo no revierten provisioning. Recuperacion rota token/hash/version; reintento inmediato reutiliza idempotency key. La entrega puede ser al menos una vez si cae el proceso justo despues de la aceptacion del proveedor.

Para fallos permanentes, revisar lastErrorCode/lastSendErrorCode y corregir la causa primero. No se ofrece reintento administrativo HTTP en HU-05. Una recuperacion operativa autorizada debe actuar sobre un job/invitacion exacto, comprobar elegibilidad, registrar la intervencion y restablecer contador/fecha/lease solo tras resolver la causa; nunca insertar tenants o suscripciones manualmente para saltar el workflow.

## Configuracion

| Variable                                | Default | Rango                                     |
| --------------------------------------- | ------- | ----------------------------------------- |
| TENANT_PROVISIONING_ENABLED             | true    | boolean; pausa tambien correos pendientes |
| TENANT_PROVISIONING_MAX_ATTEMPTS        | 5       | 1-10                                      |
| TENANT_PROVISIONING_POLL_SECONDS        | 5       | 1-300                                     |
| TENANT_PROVISIONING_LEASE_SECONDS       | 60      | 30-3600                                   |
| MEMBERSHIP_INVITATION_TTL_HOURS         | 48      | 1-168                                     |
| MEMBERSHIP_INVITATION_MAX_SEND_ATTEMPTS | 5       | 1-10 ciclos                               |

Reutiliza RESEND_API_KEY, RESEND_FROM_EMAIL y PUBLIC_APP_URL del entorno backend. La API arranca el worker automaticamente. Los tests lo invocan explicitamente o prueban start/shutdown; nunca envian correo real. No subir .env ni claves.

El correo incluye institucion, rol y enlace `/activar-cuenta#token=...`, reservado para HU-06. **HU-05 no implementa esa pantalla ni consume el token.** No se debe presentar la invitacion como cuenta activa. No hay contrasena temporal ni credenciales en la tabla administrativa. El remitente sandbox de Resend solo permite destinatarios autorizados por el proveedor; aceptacion no garantiza que el correo no llegue a spam.

## API y pantalla

`GET /api/admin/institutions`: sesion interna valida + rol OPERATOR. 401 sin sesion, 403 sin permiso, 400 ante query invalida. No crea instituciones.

- search opcional, maximo 180 caracteres: razon social, NIT, nombre/email del administrador inicial.
- activationStatus opcional: INVITED o ACTIVE, basado en membership, no en User global.
- page desde 1, pageSize por defecto 10 y maximo 100.
- Orden: reviewedAt descendente, null al final, tenantId descendente como desempate.
- Salida: items, total, page, pageSize; cada item contiene tenantId, institutionName, nit, initialAdmin.name/email, activationStatus y approvedAt nullable.
- Proyeccion limitada sin hashes/tokens/passwords ni consultas por fila. Fecha desconocida se muestra "No registrada".

React: `/admin/instituciones`, navegacion existente, busqueda/filtro/paginacion de servidor, estados loading/error/reintento/vacio, proteccion de sesion. Reutiliza Brand y estilos del backoffice; tabla desplazable en movil para conservar legibilidad. No hay lista simulada ni activacion al hacer clic.

## Verificacion

```bash
npm run prisma:deploy
npm run prisma:validate
npm run lint
npm test
npm run test:e2e
npm run build
```

El runner e2e crea bases temporales con nombres aleatorios, aplica migraciones y elimina solo esas bases al terminar. La cuenta PostgreSQL usada para tests necesita CREATEDB. La suite HU-05 tiene su propia base adicional para rollback/truncados; nunca trunca la base configurada del desarrollador. Un cierre forzado del sistema puede dejar una base temporal: verificar su nombre y que no haya proceso activo antes de limpiarla.

Cobertura HU-05: 58 casos de integracion de elegibilidad gratis/pago, snapshots, usuario reutilizado/normalizado, idempotencia, constraints, concurrencia, leases/reinicio/backoff/limites, rollback por cada escritura critica y auditoria, entrega fuera de transaccion, rotacion/hash/TTL/idempotency key, API protegida/busqueda/filtros/paginacion/fechas nulas. Diez tests React cubren listado y estados. Regresiones HU01-04 permanecen incluidas.

La comprobacion Playwright usa Nest y PostgreSQL aislados con EmailSender simulado, prueba navegacion y datos reales a 1440, 820, 390 y 320 px. Los fixtures ACTIVE solo prueban la proyeccion futura; no implementan HU-06.

## Limites deliberados

HU-06: activacion, consumo de invitacion, password y membership ACTIVE. HU-07: login institucional y contexto autorizado del tenant. Sin pagos reales, servicios distribuidos, colas externas, evaluaciones/scoring o persistencia de datos financieros de proveedores. Aislamiento de datos futuros requerira las validaciones tenant/membership correspondientes en cada HU.
