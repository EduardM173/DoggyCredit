# HU-02: Verificar correo de la solicitud

## Alcance y arquitectura

Documento Maestro, secciones 4, 12 y HU-02 de la seccion 16. `EMAIL_PENDING -> PENDING_REVIEW` solamente despues de verificar un token valido. Verificar prueba control del buzon; no legitimidad institucional, aprobacion ni provisioning. Sin HU-03, tenants, usuarios, memberships o planes nuevos.

`IdentityTenantsModule` contiene `institution-requests/` y `email-verification/`. `InstitutionRequestsService` confirma la creacion antes de llamar `EmailVerificationService`. Este usa el port `EmailSender`, enlazado por `EmailModule` a `ResendEmailAdapter`. Nest comunica componentes en proceso; solo el adapter llama a Resend. No hay colas, nuevos servicios SOA, repositorios genericos ni HTTP interno.

## Modelo y migracion

Se conserva `EmailVerificationToken`: `id` UUID, `requestId` UUID (FK a InstitutionRequest con Cascade), `tokenHash` unico, `expiresAt`, `usedAt` nullable, `createdAt`. La migracion `20260926220706_hu02_email_verification_delivery` agrega solo `sentAt` e `invalidatedAt`, ambos nullable. Los datos previos se conservan; tokens previos sin confirmacion de envio no son validos.

Se generan 32 bytes con `crypto.randomBytes`, codificados base64url (43 caracteres). PostgreSQL guarda unicamente SHA-256; nunca el token plano. El token solo permanece en memoria durante generacion/envio y verificacion. La plantilla incluye marca, CTA, expiracion y aviso de ignorar una solicitud ajena, sin NIT ni datos financieros.

## Contratos HTTP

Prefijo global `/api`. Swagger disponible en `/api/docs`.

| Endpoint POST                                     | Entrada                 | Resultado                                                                                                                                      |
| ------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `/institution-requests`                           | DTO existente de HU-01  | 201 con `id`, `contactEmail`, `status: EMAIL_PENDING`, `emailDelivery`, `retryAfterSeconds`.                                                   |
| `/institution-requests/email-verification/verify` | `{ token }`             | 200 con `contactEmail`, `status: PENDING_REVIEW`. 400 uniforme para invalido, expirado, usado, invalidado, no enviado o solicitud ya resuelta. |
| `/institution-requests/email-verification/resend` | `{ requestId }` UUID v4 | 200 con `emailDelivery` y `retryAfterSeconds`; 429 con `Retry-After` y `retryAfterSeconds` si debe esperar.                                    |

`emailDelivery`: SENT = Resend acepto y el token se activo en BD (no demuestra entrega al buzon); FAILED = envio/activacion no confirmado, solicitud guardada; UNAVAILABLE = referencia inexistente, estado no habilitado o intento superado. Reenvio no recibe correo ni devuelve identidad/estado detallado; usa el UUID impredecible ya recibido. Estados PENDING_REVIEW/APPROVED/REJECTED no generan correo.

## Consistencia y concurrencia

1. Transaccion corta toma un advisory lock por requestId, comprueba EMAIL_PENDING y cooldown, invalida reservas antiguas sin confirmar y persiste nuevo hash/expiracion. El enlace anterior enviado sigue activo.
2. Fuera de la transaccion, llama EmailSender con key `institution-request-verification/<requestId>/<tokenId>`. Una operacion conserva esa key; un reenvio explicito crea otra. Se usa la [idempotencia oficial de Resend](https://resend.com/docs/dashboard/emails/idempotency-keys).
3. Tras confirmacion, otra transaccion con el mismo lock activa `sentAt` e invalida anteriores no usados. Comprueba nuevamente estado, expiracion y que la reserva no fue reemplazada.
4. Si el envio falla, invalida solo el intento nuevo, conserva la solicitud y cualquier enlace anterior valido. Retorna FAILED; no obliga a repetir HU-01.
5. Verificacion utiliza el mismo lock, una actualizacion condicionada del token y una actualizacion condicionada EMAIL_PENDING -> PENDING_REVIEW con `emailVerifiedAt`, en una transaccion. Dos llamadas concurrentes solo pueden producir un exito. Reenvio/verificacion simultaneos no reactivan tokens despues de revisar la solicitud.

Cooldown persistente calculado sobre el intento mas reciente (`createdAt`/`sentAt`). Reserva el plazo antes de llamar al proveedor, incluso si falla, para impedir abuso/doble envio. Tras exito comienza desde `sentAt`. El frontend muestra el tiempo restante; la autorizacion siempre es backend. Una reserva interrumpida se puede reemplazar al terminar el cooldown.

Limite operativo deliberado: no hay transaccion distribuida ni outbox. Un timeout o caida entre aceptacion externa y confirmacion en BD puede entregar un enlace que no se activo; un nuevo reenvio permite recuperarse. El adapter limita a 8 segundos la espera de respuesta; el SDK puede completar la peticion externa despues, sin activar el intento descartado. Nunca se informa SENT sin confirmacion local. No se reintenta automaticamente con tokens regenerados.

## Configuracion

| Variable backend                             | Valor/desarrollo                                                                                                            |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `RESEND_API_KEY`                             | Secreto local; obligatorio en produccion.                                                                                   |
| `RESEND_FROM_EMAIL`                          | Direccion permitida por Resend; configurable.                                                                               |
| `PUBLIC_APP_URL`                             | Origen frontend, por defecto `http://localhost:5173`; HTTPS obligatorio en produccion, sin credenciales/query/hash/subruta. |
| `EMAIL_VERIFICATION_TOKEN_TTL_MINUTES`       | 30, configurable entre 1 y 10080.                                                                                           |
| `EMAIL_VERIFICATION_RESEND_COOLDOWN_SECONDS` | 60, configurable entre 10 y 86400.                                                                                          |

Para desarrollo puede usarse `onboarding@resend.dev` solo dentro de las restricciones de testing de Resend. No es remitente de produccion; para otros destinatarios/configuraciones se necesita dominio verificado segun la cuenta. Tras cambiar `.env`, reiniciar backend para recargarlo. React nunca recibe la API key. PUBLIC_APP_URL se configura explicitamente; no se deriva de Host.

## Frontend y seguridad del enlace

`/solicitud-recibida` muestra el resultado real, correo, countdown y reenvio. Conserva recibo y deadline en estado del historial de esa pestaña; backend corrige el contador con 429. Nunca almacena el token ahi.

`/verificar-correo?token=...&requestId=...` llama una vez por montaje, incluso con StrictMode, y elimina parametros al iniciar. `requestId` permite reenvio desde otra pestaña ante un token vencido; no autoriza verificacion. Tokens se mantienen solo en memoria del componente para un reintento explicito por fallo de red/servidor. No localStorage/cookies/almacenamiento global. Recargar despues de eliminar el token exige abrir de nuevo el enlace; si ya se uso, muestra error sin cambiar estado.

Exito reproduce el mockup 04: CORREO CONFIRMADO, correo, revision en proceso, siguiente decision, seguridad y contacto. Estados de error distinguen problemas del enlace de fallo de servidor/red; no afirman aprobacion. Los textos legales/contacto conservan los placeholders funcionales de HU-01 pendientes de definicion.

API envia `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, y expone Retry-After en CORS. HTML define meta referrer; Vite dev/preview envia ambos headers. En produccion, el servidor que entregue React debe enviar esos headers para `/verificar-correo` y excluir query strings de access logs/analytics. No es posible imponer headers HTTP al hosting estatico desde React: configurar el proxy/CDN al desplegar. El filtro API omite query del error y no registra excepciones/payloads crudos que puedan contener tokens/secrets. Logs de envio solo indican fallo generico.

Resend queda fijado a 6.30.0: esa version imprime errores completos en desarrollo. El adapter desactiva `logError` solo en su instancia, sin cambiar `console` ni NODE_ENV global. Es un punto de compatibilidad interno del SDK cubierto por tests; al actualizar la dependencia revisar si ofrece un logger configurable y mantener la prueba que impide filtrado.
