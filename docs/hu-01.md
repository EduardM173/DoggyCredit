# HU-01: Solicitar acceso

Actualizacion HU-02: la creacion ahora intenta enviar un correo real y devuelve ademas `emailDelivery` y `retryAfterSeconds`. La verificacion/reenvio y la extension de la pantalla de confirmacion se documentan en [HU-02](hu-02.md). Las secciones siguientes conservan el alcance original de HU-01; su exclusion del envio ya fue superada por HU-02.

## Recorrido

`/` -> `/solicitar-acceso` -> `POST /api/institution-requests` -> `InstitutionRequest` en PostgreSQL con `EMAIL_PENDING` -> `/solicitud-recibida`.

Los enlaces de cada plan incluyen `?plan=INITIAL`, `PROFESSIONAL` o `INSTITUTIONAL`. La entrada general utiliza `UNSURE`. `/iniciar-sesion` es solo una ruta informativa reservada para HU-06, sin autenticación.

El frontend usa `VITE_API_URL`, incluido el prefijo `/api`. No tiene acceso a Prisma ni a las credenciales de PostgreSQL.

## Contrato HTTP

El prefijo global existente es `/api`. El endpoint público está documentado en `/api/docs`.

```json
{
  "institutionName": "Banco de Prueba",
  "taxId": "1234567890",
  "institutionType": "BANK",
  "planInterest": "UNSURE",
  "contactName": "Ana Prueba",
  "contactRole": "Representante",
  "contactEmail": "ana@example.test",
  "contactPhone": "+59171234567",
  "representsInstitution": true,
  "acceptsTerms": true
}
```

- `201`: devuelve exclusivamente `id`, `contactEmail` normalizado y `status: EMAIL_PENDING`.
- `400`: datos inválidos, confirmaciones ausentes/falsas o campos adicionales (incluidos los administrativos).
- `409`: solicitud existente con el mismo NIT o correo normalizado. No revela datos de la solicitud anterior.
- Error de red/servidor: el formulario conserva los datos, habilita reintentar e informa que no pudo confirmar el envío.

El DTO limita longitudes al tamaño de las columnas. El NIT admite dígitos y elimina espacios/guiones, sin validar su legitimidad tributaria. El correo se recorta y pasa a minúsculas. El teléfono se normaliza a formato internacional con `+` y 8 a 15 dígitos; el formulario propone Bolivia (+591). No se verifican dominios corporativos ni datos externos.

## Persistencia y decisiones

- Se reutilizan los nombres del esquema existente: `taxId`, `contactEmail`, `contactPhone`.
- La migración `20260926210328_hu01_plan_interest` agrega únicamente `planInterest`, texto nullable para preservar registros anteriores. El DTO lo exige para nuevas solicitudes; los cuatro valores actuales se validan en código, sin enum comercial ni suscripciones.
- `contactPhone` continúa nullable en el esquema previo, pero es obligatorio en esta API.
- El servicio asigna `EMAIL_PENDING` y selecciona explícitamente los datos que persiste. Las confirmaciones del formulario no agregan almacenamiento legal.
- El control de duplicados compara NIT o correo en cualquier solicitud existente, sin importar su estado. Es la política mínima actual del servicio, no una restricción `@unique` permanente. Una política futura de re-solicitud requerirá una decisión de producto.
- Dos locks transaccionales de PostgreSQL, adquiridos en orden estable por correo y NIT, protegen la consulta y la creación ante concurrencia. Se liberan al finalizar la transacción; no se crean tablas ni workflows adicionales.
- La confirmación recibe únicamente el recibo de creación mediante el estado de navegación, conservado en el historial de esa pestaña. Abrir directamente la URL sin recibo vuelve al formulario. El correo no se agrega a URLs ni a localStorage.
- Los recursos gráficos del portátil, logo y sobre provienen de los mockups proporcionados, mostrados mediante ventanas CSS. El resto de la interfaz es HTML/React accesible y adaptable; el dashboard ilustrativo no es funcional.

## Límites de esta entrega

La pantalla de confirmación explica el próximo paso e indica expresamente que aún no se envió un enlace. No hay tokens, envío/reenvío, temporizadores simulados, verificación, transiciones, provisioning ni cuentas institucionales. Los modelos futuros ya presentes en el esquema base no se usan ni se amplían.

Los nombres y descripciones de los planes reproducen la propuesta visual; no configuran capacidades, límites ni un catálogo definitivo. Los enlaces legales muestran información de la demostración y advierten que los textos definitivos están pendientes. El canal de contacto tampoco fue proporcionado; el enlace informa su disponibilidad pendiente, sin inventar una dirección.

## Verificación

```bash
npm run prisma:validate
npm run prisma:deploy
npm run prisma:generate
npm test
npm run test:e2e
npm run lint
npm run format:check
npm run build
```

Las pruebas frontend verifican validación sin envío, plan preseleccionado, doble submit, contrato POST, navegación, correo devuelto, errores 400/409/500, fallo de red, reintento y acceso directo a confirmación. Las pruebas HTTP con PostgreSQL cubren creación normalizada, estado inicial, ausencia de entidades posteriores, obligatorios, formatos, campos administrativos y conflictos concurrentes por NIT/correo. No utilizan mocks de Prisma.
