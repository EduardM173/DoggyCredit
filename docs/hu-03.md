# HU-03: Revision y resolucion institucional

Fuente vigente: `Sprint 1 - HUs_CORREGIDO.md` y prompt HU-03. Desde HU-03 prevalecen sobre el flujo comercial anterior del Documento Maestro. HU-01/HU-02 conservan sus contratos. Ver [ADR-002](architecture/ADR-002-atomic-review-audit.md).

## Alcance y roles

Se reutilizan `User`, `PlatformRole.OPERATOR`, `InstitutionRequest` y `AuditLog`. No se crean roles traducidos ni AdminUser. Solo OPERATOR puede revisar; PLATFORM_ADMIN conserva su identificador pero no recibe implicitamente este permiso. No se requiere TenantMembership para el operador global.

`EMAIL_PENDING` no puede resolverse. Solo `PENDING_REVIEW` con `emailVerifiedAt` real puede pasar a `APPROVED` o `REJECTED`. La decision es definitiva dentro de HU-03. APPROVED autoriza a continuar en la futura HU-04, no inicia contratacion. REJECTED conserva la solicitud y no cumple la precondicion de contratacion/aprovisionamiento.

`planInterest` sigue siendo informacion comercial, nunca plan contratado, precio, capacidades ni suscripcion. No se crean Tenant, TenantMembership, TenantSubscription, MembershipInvitation, usuarios institucionales, pagos, contratos, tokens comerciales ni correos de decision. HU-04/HU-05 no estan implementadas.

## Desarrollo local

1. Aplicar migraciones con `npm run prisma:deploy` y generar cliente con `npm run prisma:generate`.
2. En `.env` local: `NODE_ENV=development`, `SEED_DEMO_OPERATOR=true`, `OPERATOR_SEED_NAME`, `OPERATOR_SEED_EMAIL`, `OPERATOR_SEED_PASSWORD` (12-128 caracteres). No subir `.env`.
3. Ejecutar `npm run prisma:seed`. Es explicito, idempotente por email y restringido a development/test. No modifica usuarios con otro rol. Un cambio de password revoca sesiones anteriores. Sin flag no crea cuentas; en production con flag falla.
4. Ejecutar `npm run dev`, abrir `http://localhost:5173/admin/login` y usar las credenciales configuradas localmente.

El seed ya no crea automaticamente el antiguo administrador sin password. No elimina usuarios preexistentes. No se incluye una password compartida en el repositorio.

## Autenticacion y sesion

Argon2id (19 MiB, 2 iteraciones, paralelismo 1). Hash dummy ante usuario inexistente y mensaje uniforme de credenciales incorrectas para cuenta inexistente, password invalida, rol no autorizado o cuenta inactiva.

Sesion opaca aleatoria de 32 bytes, hash SHA-256 almacenado en `AdminSession` (SHA-256 solo para tokens, nunca passwords). Cookie `doggycredit_admin`: HttpOnly, SameSite=Strict, Path=/api/admin, Secure en production, sin Domain. TTL absoluto configurable `ADMIN_SESSION_TTL_MINUTES`, default 120, rango 1-1440; sin refresh token. Login rota la sesion presentada. Logout revoca en PostgreSQL y borra la cookie; es idempotente aunque ya haya expirado. No hay credenciales en Web Storage ni respuestas JSON.

AuthGuard valida expiracion, revocacion y usuario ACTIVE por peticion; OperatorGuard revalida el rol. Sin sesion: 401; sesion valida sin rol: 403. POST login/logout/approve/reject exige Origin exacto a WEB_ORIGIN y `X-DoggyCredit-Admin: 1`, ademas de SameSite y CORS restringido. No hay GET mutable.

Login limitado a 10 intentos por 15 minutos por IP de socket, con Retry-After. Limite en memoria por proceso, no distribuido ni persistente. No confia en X-Forwarded-For; tras un proxy el limite agrupa por IP del proxy hasta configurar una politica explicita de proxies confiables. No es MFA ni antifraude completo.

En produccion servir frontend/API bajo el mismo sitio y HTTPS; si cambian de sitio, revisar deliberadamente cookies/CORS/CSRF, no desactivar controles. El hosting debe aplicar Cache-Control: no-store a HTML administrativo y rutas sensibles de verificacion; la API lo aplica a `/api/admin/*` y solicitudes publicas sensibles. No aplicar indiscriminadamente no-store al sitio publico. Vite incorpora esa distincion para desarrollo/preview.

## API

Prefijo `/api/admin`, documentado en Swagger:

| Metodo | Ruta                              | Contrato                                               |
| ------ | --------------------------------- | ------------------------------------------------------ |
| POST   | /auth/login                       | email, password; identidad y expiresAt, cookie         |
| GET    | /auth/session                     | identidad segura y expiresAt                           |
| POST   | /auth/logout                      | 204, revoca y limpia cookie                            |
| GET    | /institution-requests             | search, status, date, page, pageSize                   |
| GET    | /institution-requests/:id         | detalle; 404 si no existe                              |
| POST   | /institution-requests/:id/approve | cuerpo vacio; devuelve detalle APPROVED                |
| POST   | /institution-requests/:id/reject  | reason opcional, maximo 500; devuelve detalle REJECTED |

La lista devuelve items, page, pageSize, total, totalPages. Default pagina 1/tamano 10, maximo 100. Orden createdAt DESC, id DESC. Busca nombre/email sin distinguir mayusculas y NIT normalizado; no descarga todo al navegador. Estado inicial de UI: PENDING_REVIEW. Limpieza de filtros muestra todos.

No habia politica horaria de revision previa: esta implementacion utiliza dia UTC y lo identifica en la UI. Fecha ISO YYYY-MM-DD validada, rango `[00:00 UTC, siguiente dia 00:00 UTC)`. No interpreta etiquetas visuales ni cambia timestamps almacenados.

## Atomicidad y privacidad

Actualizacion condicional por id + PENDING_REVIEW + emailVerifiedAt no nulo, dentro de transaccion corta. Cero filas implica 409, incluso si desaparecio el recurso; GET inexistente es 404. Dos decisiones concurrentes: solo una gana. UI pide confirmacion, bloquea doble envio y refresca el detalle ante 409.

Identity llama al contrato `AuditWriter`; Audit es el unico propietario que inserta AuditLog. `DatabaseUnitOfWork` propaga la transaccion en proceso via AsyncLocalStorage. Si falla Audit se revierte tambien el estado. Auditoria append-only en la API: actor, accion INSTITUTION_REQUEST_APPROVED/REJECTED, entidad InstitutionRequest, id, fecha y fromStatus/toStatus. No contiene tokens, cookies, hashes, password ni PII duplicada. No se crean endpoints para modificar/borrar eventos.

No se devuelve el modelo Prisma completo. Lista/detalle no exponen tokens HU-02, session, passwordHash ni informacion financiera. Las confirmaciones legales de HU-01 no tienen evidencia persistida en el modelo actual; no se inventa una casilla auditada desde el mockup.

## Verificacion

`npm test`, `npm run test:e2e`, `npm run lint`, `npm run build`, `npm run prisma:validate` y `npx prisma migrate status`. E2E usa PostgreSQL y EmailSender simulado; no envia correos reales. Incluye autenticacion/roles/CSRF/sesion, busqueda/filtros/orden/paginacion, transiciones, concurrencia, rollback de estado y evento, y ausencia de aprovisionamiento. Fixtures identificados por ejecucion se limpian sin tocar solicitudes reales.

Limitaciones conscientes: no MFA/SSO/refresh, no gestion de usuarios, no contratacion/aprovisionamiento, no navegacion ficticia a Instituciones/Contrataciones. La retencion/limpieza operativa de sesiones expiradas queda pendiente; no permite usarlas despues del TTL. La auditoria es append-only por superficie de aplicacion, no una garantia contra un administrador directo de PostgreSQL.

Verificacion local del 2026-09-26: 13 tests unitarios API, 35 React y 78 de integracion PostgreSQL aprobados. Recorrido de navegador en 1440, 820, 390 y 320 px: login, listado, busqueda, paginacion, detalle, confirmacion, resolucion, recarga y logout; sin overflow de pagina ni imagenes rotas. Los datos temporales se eliminaron. El operador local del seed tambien autentico contra el servidor de desarrollo real.

`npm audit --omit=dev` reporto 4 alertas high en la cadena Prisma (`prisma`, `@prisma/config`, `deepmerge-ts`, `mysql2`). No se aplico `audit fix --force`: la correccion propuesta implica Prisma 6, contrario al stack Prisma 7 de esta HU. Revisar actualizaciones compatibles antes de produccion; estos checks funcionales no sustituyen esa revision de dependencias.
